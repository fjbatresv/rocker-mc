01 / THE PROJECT

A real project,
with real constraints.

As a member of Rockers 502 MC, I built its website voluntarily and with the club's approval: a digital home for its identity, history, structure, and membership requirements.

The constraints came from the club's reality: no technical team to maintain a system, no budget for its own servers, and visitors arriving on mobile. The site had to be easy to update, fast, and dependable.

Visit the club's website ↗

02 / DECISIONS

Each choice has a reason.

01

No framework or build step

Direct HTML, CSS, and JavaScript mean the site ships as it is written. There are no dependencies to update or compilation steps that can fail.

What a site like this gives you Less maintenance and a deliverable anyone can inspect.

Explore the site files ↗

02

Measured accessibility

The red text color meets AA contrast. The site has visible focus, an Escape key menu close, reduced motion, and generous touch targets for the carousel controls.

What a site like this gives you More people can use it, with less friction on phones and keyboards.

CSS ↗ · JavaScript ↗

03

Verifiable security

The CSP rejects inline scripts. Security checks run in CI, Actions are pinned by SHA, and AWS uses temporary OIDC credentials.

What a site like this gives you Less attack surface and deployments without permanent keys.

Policies ↗ · CI and deployment ↗

04

Weight under control

Photos use WebP. The favicon went from 338 KB to 52 KB. The site's JavaScript is small and optional: navigation and content remain available without it.

What a site like this gives you Less data to download and a faster experience on mobile networks.

Measured favicon change ↗

05

Technical SEO, clearly labeled

Structured JSON-LD, a canonical URL, sitemap, social metadata, and a custom 404 page. The content makes clear that this is the club's website.

What a site like this gives you Better context for search and shared links, with a clear way out of errors.

Metadata ↗ · Sitemap ↗

03 / ARCHITECTURE

Small in the browser.
Clear in production.

Every pull request blocks regressions with automated checks. The club's website deploys to a private bucket; CloudFront serves it with the security header policy. The landing lives on GitHub Pages, on its own domain.

04 / PROCESS

Plan, build,
verify.

The cycle was explicit: written plan → Codex implements → Claude coordinates and reviews → automated checks → pull request. Agents helped carry out the work; decisions and club approval remained human.

There was a real mistake, too: PR #2 published the wrong domain. I caught it while reviewing the live site. PR #3 fixed it and strengthened the verifier so it would not happen again. See an implementation plan ↗
