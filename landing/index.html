01 / EL PROYECTO

Un proyecto real,
con límites reales.

Como miembro de Rockers 502 MC, construí de forma voluntaria y con aprobación del club su sitio: una casa digital para su identidad, historia, estructura y requisitos de ingreso.

La realidad definió el trabajo: un club sin equipo técnico para mantener un sistema, sin presupuesto para servidores propios y con visitantes que llegan desde el celular. El resultado debía ser fácil de actualizar, rápido y confiable.

02 / DECISIONES

Decisiones con un porqué.

01

Sin framework ni build

HTML, CSS y JavaScript directo hacen que el sitio se publique como se escribe. No hay dependencias que actualizar ni compilación que pueda fallar.

Qué gana un sitio así Menos mantenimiento y una entrega que cualquiera puede inspeccionar.

Ver los archivos del sitio ↗

02

Accesibilidad medida

El rojo de texto se ajustó a contraste AA. Hay foco visible, menú que cierra con Escape, movimiento reducido y objetivos táctiles amplios en el carrusel.

Qué gana un sitio así Más personas pueden usarlo; menos fricción en móvil y teclado.

CSS ↗ · JavaScript ↗

03

Seguridad verificable

La CSP no acepta scripts en línea. Los verificadores corren en CI, las Actions se fijan por SHA y AWS recibe credenciales temporales con OIDC.

Qué gana un sitio así Menos superficie de ataque y despliegues sin llaves permanentes.

Políticas ↗ · CI y despliegue ↗

04

Peso bajo control

Las fotos usan WebP. El favicon pasó de 338 KB a 52 KB. El JavaScript del sitio es pequeño y opcional: la navegación y el contenido siguen disponibles sin él.

Qué gana un sitio así Menos datos descargados y una experiencia más rápida en redes móviles.

Cambio medido del favicon ↗

05

SEO técnico, sin disfraz

Datos estructurados en JSON-LD, URL canónica, sitemap, metadatos sociales y una página 404 propia. El contenido deja claro que es el sitio del club.

Qué gana un sitio así Mejor contexto para buscadores y enlaces compartidos; errores con salida clara.

03 / ARQUITECTURA

Pequeño en el navegador.
Claro en producción.

Cada pull request bloquea regresiones con verificaciones automáticas. El sitio del club se despliega a un bucket privado; CloudFront lo sirve con la política de cabeceras. La landing vive en GitHub Pages, en su propio dominio.

04 / PROCESO

Planear, construir,
verificar.

El ciclo fue explícito: plan escrito → Codex implementa → Claude coordina y revisa → verificadores automáticos → pull request. Los agentes ayudaron a ejecutar el trabajo; las decisiones y la aprobación del club siguieron siendo humanas.

También hubo un error real: el PR #2 publicó un dominio equivocado. Lo detecté al revisar el sitio en vivo. En el PR #3 quedó corregido y el verificador se endureció para evitar que vuelva a pasar. Ver un plan de implementación ↗
